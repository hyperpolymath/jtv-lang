The proof-status file for this repository, recording which prover carries which
obligation and the *strength* of each result, under the estate rules. It exists
because JtV claims proofs (README, EXPLAINME §7, AFFIRMATION), which makes a
ledger mandatory (`standards/docs/README-EXPLAINME-STANDARD.adoc` §5).

*Normative sources — this file follows them, and where it disagrees with them
they win:*

* `hyperpolymath/standards` → `3-practice/PROOF-POLICY.adoc` — which prover
  carries which obligation (§1 mapping), how theory proofs are rechecked (§2),
  re-homing of existing proofs (§3), exceptions (§4), status vocabulary (§5).
* `hyperpolymath/standards` → `docs/README-EXPLAINME-STANDARD.adoc` §5 — the
  closed proof-ledger vocabulary.
* `hyperpolymath/standards` → `3-practice/PROOF-POLICY.adoc` §8 — *Proof Witness
  Grades* (owner ruling 2026-11-04). Grades are written `PWG-3`, `PWG-2i`,
  `PWG-2ii`, `PWG-1` or `ungraded`, are *derived from receipts* and are never
  asserted by hand. In this repository they are derived by
  `crates/jtv-proof-ledger` into `verification/ledger/PWG.adoc` (§4), and CI
  fails if that file drifts from the receipts.
* `hyperpolymath/mathesis` → `docs/proposals/estate-mathematical-architecture.adoc`
  — the *unratified* brief that PROOF-POLICY §8 adopted with corrections. It is
  provenance only; where it differs from §8 (its Grade 2ii, its Grade 1 checker
  services), §8 governs.
* `verification/PROOF-CAPABILITY-MATRIX.adoc` — JtV's own detail matrix
  (per-library, per-theorem). This file is the ledger summary that matrix feeds.

== 1. Conformance summary — the honest headline

JtV was an *engineering-first* project with a *Lean-first* theory layer. Since
2026-11-01 it also has an **Agda theory layer** for part of its model
(`theory/agda/`, four modules), which is what makes a Proof Witness Grade
derivable at all. The current receipts are `verification/receipts/agda.json` and
`verification/receipts/lean.json`; the derived grades are in §4. As of
2026-11-09 every Agda theorem has a Lean declaration of the same strength except
`loss-is-real`, whose Lean counterpart `residue_lossy` is a weaker existential
(recorded in `theorems.json`), so the Lean development is a candidate *leg*; it counts only once the owner records each
comparison as `RECONCILED` (PROOF-POLICY §2.2, §8.2).

== 3. Verification commands and their toolchain requirements

[source,bash]
----
# Theory (Agda — the estate source of truth; this is the receipted one)
( cd theory/agda && ./check.sh )     # pin: Agda 2.7.0.1, agda-stdlib 2.4

# Theory (Lean leg) — run from the repo root: a bare
# `cd jtv_proofs` would persist and break the commands below it.
( cd jtv_proofs && lake build )      # pin: leanprover/lean4:v4.12.0
grep -rnwE 'sorry|admit|axiom' jtv_proofs/*.lean   # must be empty

# Engineering (Idris2 ABI)
idris2 --check src/abi/Types.idr

# Engineering (Rust behaviour — tested-only)
cargo test --all

# Receipts and grades (PROOF-POLICY §8). A receipt is written only when its
# checker run succeeds; `check` needs no prover and is what CI runs.
AGDA_STDLIB=/path/to/standard-library.agda-lib \
  cargo run -p jtv-proof-ledger -- receipt agda   # runs theory/agda/check.sh
cargo run -p jtv-proof-ledger -- receipt lean     # lake build + #print axioms
cargo run -p jtv-proof-ledger -- render           # writes verification/ledger/PWG.adoc
cargo run -p jtv-proof-ledger -- check            # fails if PWG.adoc has drifted
----

*Toolchain honesty (PROOF-POLICY §6).* A session without Agda, Rocq/Lambdapi, or
Creusot/Why3 **cannot run those legs**, and must say so rather than report them
passing. The session that wrote this ledger had none of them. Adding them belongs
in `setup.sh` (agent sessions) and the Guix manifest/container (CI) per
`standards/LANGUAGE-POLICY.adoc` §2.

*Recorded deviation — CI install route.* `.github/workflows/agda-proof-policy.yml`
installs the upstream Agda 2.7.0.1 release binary (sha256-pinned), the matching
primitive library from the pinned source commit, and agda-stdlib 2.4 at a pinned
commit, rather than through a Guix manifest or container, because this repository
has no such manifest or Agda image (the only `Containerfile` is
ClusterFuzzLite's). Until 2026-11-09 it installed the PyPI `agda` wheel instead,
which the estate's Python ban does not permit; this ledger previously described
that route, inaccurately, as building from tagged sources. The job
compensates by asserting the *installed* stdlib library name against this
project's `depend: standard-library-2.4`, so a silent substitution fails rather
than passes. This is a documented exception, not compliance; the remediation is
an Agda entry in the estate manifest. The same workflow notes why its action
references stay version-tagged (the repository's `actions.lock` is generated from
tags) and takes the credential half of that fix (`persist-credentials: false`).

== 4. Proof Witness Grades (PROOF-POLICY §8)

The section below is generated: `crates/jtv-proof-ledger` derives every grade
from the receipts in `verification/receipts/` and the records in
`verification/ledger/theorems.json`, and CI fails when it drifts. A receipt counts
only while the sha256 digests it recorded still match the files on disk (§8.4).
The two provers' receipts go stale independently. Editing an Agda input drops
every theorem to `ungraded` until `receipt agda` is re-run, because no Agda leg
then counts. Editing a Lean input stops every Lean leg counting until
`receipt lean` is re-run; theorems with a current Agda receipt stay `PWG-3`. Grades are reported as a census with its denominator, never as a
percentage.

=== 4.1 Topics the grades do not cover

These rows use the closed §5 vocabulary. Engineering obligations are not on the
PWG ladder (§8.1).

[cols="2,1,3",options="header"]
|===

=== 5.1 The Rust route (Creusot with Pearlite, and Verus) — and the Aeneas temptation

PROOF-POLICY §1.2 puts JtV's core runtime under Creusot, with contracts written
in Pearlite, and Verus as the complementary default verifier. None of the three
appears in the repository, so every behavioural claim about
`reversible.rs`/`interpreter.rs` is currently `tested-only` at best. Using both
verifiers does not raise any theory theorem's Proof Witness Grade (§1.2, §8).

Aeneas is *the* estate route for "Rust code implements a theorem proved in a
proof assistant" (§4.1), which is exactly JtV's `gap-001`. It is **not** adoptable
today, and the reason is policy, not preference:

* Aeneas's Rocq backend carries an axiom (`mk_array`) from which `False` is
  derivable and is unmaintained → cannot support any status above `ASSUMED`.
* Aeneas's Lean backend depends on Mathlib, which §2 rules out estate-wide.
* Therefore the Rust↔model correspondence row is `ASSUMED` at best, and the
  model theorem stays `proven` only because its own kernel check is independent.

Recorded so a future session does not "close the proof-to-interpreter gap" with
Aeneas and then report the implementation as proved: per §4.1 that would be two
rows — `proven` for the model, `ASSUMED` for the correspondence — and needs a
recorded owner decision to adopt the backend at all.
