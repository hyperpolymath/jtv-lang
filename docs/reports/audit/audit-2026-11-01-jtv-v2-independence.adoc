[.lead]
*Question.* Is JtV v2 still an independent research-language programme, or has
it drifted into an assumed dependency on sibling hyperpolymath projects —
specifically `epistemic-types` (at `5422cd5`), *JanusKey*, and *Absolute Zero* —
on the strength of shared reversibility/epistemic vocabulary?

*Answer.* Independent. There is no code, build, or runtime dependency on any of
them, and none is introduced here. This audit records what JtV's reversibility
mechanism *actually is* at each layer, what the proof-to-interpreter gap
actually is, what "v2" means today, and the precise shape any future adapter
would have to take to be admissible. The connection proposed by the vocabulary
overlap is recorded as *related work only*.

*Scope of evidence.* Static audit of this tree at `b23f8e9` (the full repository
was read; every claim below cites a file, and line numbers are as of this
commit). *No* `cargo`, `rustc`, `lake`, or Lean toolchain is available in the
audit environment and `crates.io` is not reachable, so *nothing here is a
test-run result*. Findings that would normally be confirmed by execution are
marked **[not executed]** and are stated as static-reading claims, not as
reproduced failures.

| # | Question | Finding

| V1

| *No.* No entry in `Cargo.toml`, `Cargo.lock`, `flake`/`mise`/`Justfile`, no

=== 1.1 What a dependency would have to look like

For a Rust workspace, an actual dependency is one of: a `[dependencies]` entry
(path, git, or registry), a `Cargo.lock` entry, a build-script invocation, an
FFI/`extern "C"` boundary, a submodule, or a runtime protocol spoken over I/O.
Anything less is *related work*.

of "similar vocabulary" the brief warns against reading as convergence. The
semantics differ: JtV's CNO is a *runtime identity check over an interpreter
state map*; Absolute Zero's is a *multi-prover obligation about a categorical
construction*. Neither cites the other.

=== 1.4 The `epistemic-types@5422cd5` item

The stated context is that `epistemic-types` is a *constructive epistemic
library* and supplies *no reversible-language runtime*. That is consistent with
everything found here: JtV contains a complete reversible-language runtime of
its own (`reversible.rs`, `interpreter.rs` token store, Lean `RevOp` model), so
there is nothing for it to have borrowed a runtime from, and nothing in this
tree asks for one.

The one real adjacency is *terminology*, and it is worth stating precisely
because it is the most likely source of a false convergence claim:

[cols="1,3,3",options="header"]
|===
| Word | JtV meaning (this repo) | Not to be conflated with

| *Echo*
| Graded *structured loss* `{Safe ⊑ Neutral ⊑ Breaking}`, a coeffect-style
grade carried in the arrow (`echo.rs`, `ast::Echo`, ADR-0009 D1).
| A generic `Σ`-type or a wrapper; or any epistemic-types construct.

| *Epistemic*
| Graded *observability* `{Opaque ⊑ Partial ⊑ Transparent}` — a second axis,
*dual* to Echo (loss vs revelation), forming a product effect row
(`epistemic.rs`, ADR-0009 D2).
| Knowledge/belief modalities in the epistemological sense. JtV's grade is a
static, syntactic, worst-case analysis of a function body
(`function_epistemic`, `epistemic.rs:52`).

| *ReversalToken*
| JtV-local opaque `Value::ReversalToken(u64)` indexing an in-process
`HashMap<u64, Vec<RecordedOp>>` (`number.rs:26`, `interpreter.rs:30`).
| A shared ABI, a linear type in the type system, or the token of any other
project.
|===

One note for accuracy: JtV's vocabulary *is* shared with `echo-types` (Agda),
which JtV explicitly names as its conceptual reference. If `epistemic-types` and
`echo-types` are related artefacts, that relationship does **not** transitively
become a JtV↔`epistemic-types` dependency: JtV's only claim about `echo-types`
is "our lattice instantiates the same fibre construction" (`JtvEcho.lean` §4),
which is *related work* by definition — it is a correspondence between two
mechanisations, not a link. No action is taken on it here.

== §2 "Snapshot-based `ReversalToken`": what the mechanism actually is

The phrase is half-right, and the half that is wrong matters, because three
layers implement three different things under one name.

=== 2.1 Layer A — the Rust runtime token (the real one)

`reversible { ... } -> tok` runs the body forward through
`ReversibleInterpreter::execute_forward` and *records concrete operations* into
a `ReverseTrace`; the trace is moved out (`take_recorded_ops`) into
`Interpreter::token_store: HashMap<u64, Vec<RecordedOp>>` keyed by a monotonic
`next_token_id`, and `tok` is bound to `Value::ReversalToken(id)`
(`interpreter.rs:452-482`). `reverse tok` removes the log and applies each op's
*inverse* last-to-first (`apply_inverse_ops`); `abandon tok` drops the log. The
token is consumed by removal, so `reverse`/`abandon` twice errors at runtime
(`reversibility_c2_tests.rs` C2-3/C2-4).

`RecordedOp` has four variants (`reversible.rs:11-28`):

* `AddAssign { target, value }` — inverse is `SubAssign` (subtract the *recorded*
  value, not a re-evaluated expression);
* `SubAssign { target, value }` — inverse is `AddAssign`;
* `If { condition_was_true, then_ops, else_ops }` — inverse replays the branch
  that *was taken* (`apply_operation`);
* `Snapshot { target, old_value }` — the *residue*: for a self-referential step
  (`x += x`) the pre-step value is saved and restored, because the naive
  `-value` inverse is wrong there.

So the default is an **operation log**, and a **snapshot is used as the
residue-recovery mechanism for the Neutral tier only**. That is the opposite of
007's Phase-1 whole-block snapshot restore, which the canonical design doc
explicitly rejects (`docs/language/DESIGN-JTV-V2-REVERSIBILITY.adoc`, "What JTV
v2 Does NOT Do").

=== 2.2 Layer B — the tokenless `reverse { }` path is *not* the log

`reverse { ... }` (no token) does not replay the log. `Interpreter::eval_reverse_block`
constructs a fresh `ReversibleInterpreter` over `globals.clone()` and calls
`execute_inverse` (`interpreter.rs:412-441`), which walks the *AST* backwards and
recomputes each inverse against the current state (`reversible.rs:177-224`).

Two behaviours therefore coexist for the same source construct:

[cols="2,2,3",options="header"]
|===
| Aspect | Token path (`reversible { } -> tok`) | Tokenless path (`reverse { }`)
| Undo of `x += e`
| subtract the *recorded* value
| subtract `e` *re-evaluated* on the reversed state
| Conditional
| replays the branch that was recorded as taken (`condition_was_true`)
| *re-evaluates* the guard in reverse and skips if it no longer holds
| Self-reference `x += x`
| admissible when a token is bound; residue snapshot restores exactly
| rejected by the typechecker (Safe-only); the runtime has no such check
| Overall state
| whole `HashMap` cloned into a scratch interpreter and copied back
| idem
|===

Both paths therefore do whole-state copying at the block boundary even though
neither relies on it for correctness. That is an implementation detail (state
marshalling), *not* the semantic mechanism — worth stating plainly, because it is
the most likely reason a reader describes JtV's tokens as "snapshot-based".

Note the tokenless conditional is the one place where re-evaluation can *fail to
undo*. The grammar allows only a plain assignment inside a reversible `if` branch
(`reversible_stmt = reversible_assignment | if_stmt`, and the branch body is a
control `block`), so the demonstration has to use `=`:

[source,jtv]
----
x = 4
reverse { if x < 5 { x = 5 } }
----

Forward: the guard holds, the branch assigns `x = 5` - and records nothing.
Reverse: the guard is re-evaluated at `x = 5` => false => the undo is skipped, so
`x` stays `5`. The block is not the identity. (This program is syntactically
valid; an earlier draft showed `x += 1` inside the branch, which the parser
rejects - corrected after review.)
in the reverse direction (the comment at `reversible.rs:204` invokes exactly that
requirement) — but JtV has no check for it. See F3 in §8. **[not executed]**

=== 2.3 Layer C — the Lean model's "token" is an `Int`

`jtv_proofs/JtvTheorems.lean:383`:

[source,lean]
----
def RevOp.execBackwardWithToken (op : RevOp) (σ : State) (tok : Int) : State :=
  match op with
  | addAssign x _ => σ[x ↦ tok]
  | subAssign x _ => σ[x ↦ tok]
----

`rev_forward_backward_with_token` proves that restoring `x` from the saved
pre-step value recovers the whole state, unconditionally (including
`x ∈ e.freeVars`), and `rev_backward_naive_fails_self_ref` proves the token is
*necessary* in that case. This is a correctly-shaped, non-vacuous result — and
it is a **single-operation residue snapshot**: `tok : Int` is one saved value of
one variable, not a log, not multi-step, not a carried structure.

=== 2.4 What follows

"Snapshot-based `ReversalToken`" is a description of Layer C and of the
`RecordedOp::Snapshot` residue. It is *inaccurate* as a description of the v2
runtime token (a multi-op log) and *inaccurate* as a description of the design
intent. The repo's own `README.adoc` currently repeats the inaccurate version
("Snapshot-based rollback of local state") and is corrected in this change.

The honest one-line statement is: **v2's token carries a per-operation inverse
log; a saved-value snapshot is used as the residue that makes Neutral
(self-referential) steps invertible; the mechanised model so far covers one
operation's residue, not the log.**

== §3 The proof-to-interpreter gap

=== 3.1 What exists

`verification/PROOF-CAPABILITY-MATRIX.adoc` is the authority and is candid:
`JtvCore`, `JtvTheorems`, `JtvOperational`, `JtvTypes`, `JtvSecurity`,
`JtvExtended`, `JtvEcho` are `verified` (Lean 4, no `sorry`/`admit`/added
`axiom`), and `gap-001` (`interpreter ↔ denotational-model correspondence`) is
`partial` with a *tested* correspondence harness (`mod
denotational_correspondence` in `interpreter.rs`): the same four `evalDataExpr`
rules re-encoded in `i128`, a shared golden corpus, and exhaustive checking of
every integer-fragment expression of height ≤ 2 (~12k cases). The matrix states
its own bound: integer fragment, in-range, exhaustive-up-to-depth, "not a
Lean-mechanised refinement of the evaluator".

=== 3.2 What does not exist — enumerated, because "the gap" is often left vague

. *No extraction or refinement.* There is no `lake` extraction into Rust, no
  generated code, no proof-carrying artefact consumed by the interpreter. `lake
  build` and `cargo test` are independent gates over independent artefacts
  (`proof-regression.yml` vs `rust-ci.yml`).
. *No shared token representation.* Lean: `tok : Int`, one variable, one op.
  Rust: `Vec<RecordedOp>`, many ops, four variants, per-op recorded values.
  Nothing states that the Rust log *refines* the Lean residue, and for
  multi-operation blocks the Lean model cannot even be instantiated — the
  theorem is per-`RevOp`.
. *Conditionals are outside the model.* Lean `RevOp` has `addAssign` /
  `subAssign`. The Rust `RecordedOp::If` and the tokenless branch/guard
  re-evaluation have **no Lean counterpart at all**, so the conditional reversal
  paths — the two that already disagree with each other (§2.2) — are unverified
  in both directions.
. *The type-level gate is proved, the runtime gate does not exist.* The Lean
  admissibility theorems (`blockEcho_admissible`,
  `blockEcho_admissibleWithResidue`) are realised in `typechecker.rs`
  (`check_echo_admissible` / `check_echo_admissible_with_residue`). But the
  interpreter itself performs *no* admissibility or reversibility check:
  `Interpreter::run` (`interpreter.rs:183`) evaluates statements directly. The
  gate holds only on paths that typecheck first. Only `jtv run` does that
  (`run_file`, `main.rs:199-222`, "SECURITY: Run type checking before
  execution"). These shipped paths do **not**:

  * **REPL** — `crates/jtv-cli/src/repl.rs` calls `parse_program` then
    `Interpreter::run` with no `TypeChecker`;
  * **debugger** — `crates/jtv-debug/src/main.rs` likewise;
  * **WASM** — `WasmInterpreter::run` / `run_and_collect` parse and execute
    (`wasm.rs:69-92`); `type_check` is a separate, host-opt-in method;
  * **any embedder** — `parse_program` + `Interpreter::run` is the public API,
    and the reversibility test suites use exactly that.

  So F1-F3 are reachable interactively in the REPL and debugger, in the
  playground, and from any library host - not only in unusual embedding
  scenarios.
  silently gets unchecked reversal.
. *`check_reversibility` is production-dead.* The AST-level guard in
  `reversible.rs:471` is referenced only by tests
  (`tests/contract_tests.rs:242,260`); the typechecker has its own, different
  Echo-based guard which *is* the proved rule's realisation in code, but which
  the interpreter never consults on its own path. Two guards, one dead, the
  other opt-in.
. *No end-to-end round-trip at the integration level.* `STATUS.adoc` lists this
  under Known Gaps and it is still true: there is no
  `(forward ∘ reverse = id)` test over the *language surface* for the Neutral
  tier. The residue bridge is tested at `ReversibleInterpreter` unit level
  (`test_neutral_self_reference_recovered_via_residue`) and the token paths are
  tested for Safe-only blocks (`reversibility_c2_tests.rs`); the composition —
  `reversible { x += x } -> tok` through parser, typechecker, interpreter and
  `reverse tok` — is not in the suite.

=== 3.3 Why this is a research obligation, not a defect report

The gap is *the state of the art JtV claims to be at*, and it is documented as
such. Recording its shape precisely is what keeps the claim honest: JtV has a
mechanised model of its semantics, a tested correspondence for the integer
fragment, and a typed admissibility rule realised in the checker — but the
*reversible* semantics is mechanised one operation at a time while the runtime
implements a log with conditionals. Any statement of the form "JtV's
reversibility is proved" must be read as "the Safe single-step and the Neutral
residue step are proved; the token/log semantics as executed is tested, not
proved".

=== 4.1 Status of the surrounding documentation

Three artefacts are stale in ways that would mislead the next reader, and are
corrected in this change:

. `README.adoc` §v2 Reversibility — "Snapshot-based rollback of local state",
   "`ReversalToken` is linearly typed", and `irreversible { }` as if it existed.
   No one of these three is true of the implementation (§2, §4 table).
. `spec/jtv_v2_type_system_corrected.adoc` §9 — an implementation note dated
   2026-06-02 saying the residue mechanism is "unimplemented, so the checker
   conservatively rejects [Neutral]". That was superseded on 2026-06-15
   (ADR-0007, the `(c)` bridge); the note is now the opposite of the code.
. `docs/language/reversibility/current-status.adoc` — "limited, partial
   reversibility … no reverse execution model … not enforced at the language

=== 4.2 One status item worth flagging separately

`reversible { ... }` with **no** `-> tok` binding is legal (the grammar makes the
binding optional, `grammar.pest:59`) and stores the log anyway; the interpreter
comments that it is "effectively abandoned"
(`interpreter.rs:472-473`). The log is then unreachable and retained for the
interpreter's lifetime — residue that can never be recovered and is never freed
until `reset()`. Either the binding should be mandatory, or the tokenless form
should be a *Safe-only* `reverse`-style block that records nothing. Flagged, not
changed (it is a semantics decision, not a doc fix).

== §5 What this audit does *not* touch — JtV's own scope

JtV's research identity is stated independently of every sibling project, and
nothing in this audit relaxes it.

*The Harvard Data/Control split* is JtV's, and it is structural, not
editorial: `Language`/`Expr` GADT separation in Idris2 (`src/abi/Types.idr`,
`isControl` + `dataIsNeverControl`), the grammar-level separation in
`grammar.pest`, `no_control_to_data_flow` and `string_not_executable` in
`JtvSecurity`, the addition-only Total Data plane (ADR-0007 D1), and the AOLD
grafting claim (D3). Reversibility lives *inside* Control's reverse blocks, as a
third orthogonal axis, and is explicitly not allowed to erode Data totality or
purity (ADR-0007, "Identity preserved").

*JtV's reversibility obligations are its own and were stated before, and
independently of, any portfolio question*:

[cols="1,4",options="header"]
|===
| Obligation | Source (JtV-internal)

| Subtraction is not a primitive; it is the reversal of addition
| ADR-0007 D2; DESIGN-JTV-V2-REVERSIBILITY "Philosophical Commitment"

| Addition-only, no multiplication primitive, all number systems
| ADR-0007 D1

| Turing-completeness by Harvard block *embedded* in a von-Neumann host (AOLD)
| ADR-0007 D3

| Shortest-addition-path-to-equality, with Echo as lineage
| ADR-0007 D4

| Reversal *ladder*: Safe → Neutral (retained residue) → Breaking
| ADR-0007 D5; `Echo` lattice; `admissible` / `admissibleWithResidue`

| Echo tier fixed by the additive algebra of the carrier
| ADR-0007 D6; ADR-0010 (`abelianGroup`/`approxGroup`/`nonGroup`); `JtvEcho` §6

| Reverse blocks: all statements invertible, no `EchoBreaking`, no loops
| spec v2 §9; `check_echo_admissible`

| Two independent effect axes (Echo loss, Epistemic revelation) as a product row
| ADR-0009 D1/D2/D3; `effect.rs`

| Locally reversible only; cross-agent sends are a static error
| DESIGN §The ExternalHandle Boundary
|===

None of these obligations is derived from, delegated to, or weakened by
`epistemic-types`, *JanusKey*, or *Absolute Zero*. Conversely, this audit does
not ask JtV to *adopt* anything: the "do not introduce a dependency merely
because all three discuss reversibility" instruction is honoured by leaving the
dependency graph exactly as it is.

=== 6.1 Janus (Lutz & Derby 1982; Yokoyama & Glück 2007)

*Relation:* literature lineage. JtV's per-operation reversal — and the
"guard must hold when reversing" discipline — is the Janus tradition, and the
comment at `reversible.rs:204` invokes it by name. This is citation, not
coupling: no Janus implementation, grammar, or artefact is imported, and Janus
is a published language, not a hyperpolymath component.

*Divergence worth keeping explicit:* Janus guarantees reversibility by
*construction* (there is no irreversible assignment in the language). JtV
guarantees it by *grading + gate* (Echo classification, an admissibility rule
in the checker, and a residue token where the grade is Neutral). That is a
different research position — JtV keeps a total, addition-only Data plane and an
expressive Control plane and pays for it with a static gate — and it is the
reason JtV's obligations cannot be discharged by importing Janus's.

=== 6.2 The 007 Phase 1/Phase 2 fork

*Relation:* a *deliberately designed experiment* between two of the author's own
implementations, documented in both directions
(DESIGN-JTV-V2-REVERSIBILITY "The Designed Fork with 007"). Shared: linear
token pairing, `Option<token>` at asymmetric joins, `ExternalHandle` static
error, `irreversible { }`, structural sugar. Different: snapshot-and-restore
(007 Phase 1) vs operation log (JtV v2).

This is the one place where a *shared mechanism* is claimed, and it is claimed
narrowly: pairing mechanism shared; reversal semantics not. It carries no code
dependency and no build coupling — the shared part is a design vocabulary the two
implementations keep in sync by reading each other's design docs.

=== 6.3 Absolute Zero

*Relation:* sibling verification programme, different subject. Absolute Zero
mechanises *Certified Null Operations* across Coq/Lean/Agda with an axiom-triage
discipline; JtV uses "CNO" as the name of a *runtime identity property*
(`execute_and_reverse`). Shared vocabulary: "CNO", "reversibility",
"Landauer/Bennett". Shared artefact: none.

If a connection is ever wanted, the honest form is: *Absolute Zero's CNO
definition could serve as an external specification of what JtV's
`execute_and_reverse` is supposed to mean.* That is a specification-adoption
proposal — a research claim requiring a semantic mapping — not a dependency, and
it is **not** proposed here (see §7.3).

=== 6.4 JanusKey

*Relation:* different domain sharing a word. JanusKey is architecturally
reversible *file operations* over content-addressed storage (SHA256 + audit
trail + transactions) in Rust. JtV is a *language* whose reversibility is a
semantic property of programs over an abstract state map. There is no shared
abstraction to depend on: JanusKey's reversibility is at the filesystem API
layer; JtV's is at the expression/evaluation layer. Nothing in JtV's `Storage`,
`ExternalHandle`, or coprocessor surfaces would be served by JanusKey, and
JanusKey has nothing to import from a language runtime.

=== 6.5 `epistemic-types@5422cd5`

*Relation:* as stated in §1.4 — constructive epistemic library, no reversible
runtime, no artefact cited by JtV, no code path. Similar vocabulary
("epistemic", "reversible") is documented here as *false-positive signal*, not
as convergence evidence. Architectural convergence would require an actual
correspondence between JtV's effect row and that library's constructions, proved
or at least stated as a mapping; no such correspondence is claimed anywhere in
this tree, and this audit does not create one.

== §7 If an adapter is ever wanted: explicit admissibility semantics

Nothing below is planned, scheduled, or implied by this audit. It is written
down so that a future proposal cannot be accepted on vocabulary alone. An
adapter from JtV to any of the above is admissible only if *all* of the
following hold.

=== 7.1 Required form

. *Direction: JtV-internal model → external artefact as a target of a mapping.*
   The external project supplies *theory or specification*; it never supplies a
   runtime, a token representation, a store, or an evaluator. Any proposal in
   which JtV would obtain its reversible runtime from outside is rejected on its
   face, because JtV *is* a reversible-language runtime.
. *Authoritative side stays JtV.* `verification/PROOF-CAPABILITY-MATRIX.adoc`
   and `JtvEcho.lean` remain authoritative for JtV implementation semantics, as
   they already do for the `echo-types` reference. An external development is
   never allowed to overrule the matrix.
. *Pinned and named.* The proposal must cite a commit (e.g.
   `epistemic-types@5422cd5`), the exact artefact, and which direction data would
   flow. Prose references to a repository are not an adapter.
. *No shared ABI.* No shared token type, no shared serialisation, no shared
   store. If the mapping needs a token at the boundary, the boundary is wrong.
. *Additive only.* An adapter must not change JtV's obligations (§5), the
   Data/Control split, the addition-only mandate, or the Echo/Epistemic axes.
   If it would, it is a redesign and needs its own ADR, not an adapter.
. *Failure is a documented non-mapping.* If the correspondence cannot be stated
   (different notions of loss, different notions of knowledge, no shared fibre
   construction), the outcome is a "Related work, no mapping" note in this
   directory — which is a successful audit outcome, not an unfinished task.

=== 7.2 What each candidate would have to supply to be more than related work

[cols="2,4",options="header"]
|===
| Candidate | The missing artefact

| `epistemic-types`
| A stated correspondence between its constructions and JtV's
  `Echo × Epistemic` product row — i.e. which of its objects, if any, is the
  interpretation of `function_effect` — plus confirmation that no runtime
  obligation is implied. Without that, the relation is vocabulary.

| Absolute Zero

  standard (runtime test + tested correspondence) is lower than Absolute Zero's
  (multi-prover, triaged axioms). Adopting the definition without meeting the
  standard would be a downgrade dressed as integration.

| JanusKey
| Nothing available: the abstraction levels do not meet. Recorded as
  non-adjacent.

| Janus
| Nothing available: published literature, cited as lineage (§6.1). No adapter
  is definable to a paper.
|===

**Status: none proposed.** The default for all four is "related work, no

== §9 Estate conformance: which grade does any of this earn?

Folded in 2026-11-01 at the owner's direction: the governing policies are
`hyperpolymath/mathesis` → `estate-mathematical-architecture` (§5 graded proof
architecture, §6 epistemic precision) and `hyperpolymath/standards` →
`3-practice/PROOF-POLICY.adoc` (§1 prover mapping, §2 rechecking, §3 re-homing,
§4 exceptions, §5 vocabulary). JtV now carries a ledger at
`verification/PROOF-STATUS.adoc`; this section is the audit-level summary.

=== 9.1 The grade definitions that matter here

* *Grade 3* — the theorem type-checks **locally in Agda** under strict flags
  (`agda --safe --without-K --cubical-compatible`), not yet translated to an
  independent foundation.
* *Grade 2i / 2ii* — the **Agda witness** is translated to one / two other
  foundations (2ii's second must be non-DTT, e.g. Isabelle/HOL, because
  Agda/Rocq/Lean share the DTT-CIC family).
* *Grade 1* — those witnesses compile headless in CI via verified checker APIs
  (AXLE for Lean, coq-lsp for Rocq, Isabelle server for HOL), receipt pinned to a
  commit.
* Statuses are `Open` / `Claimed` / `Grade 3` / `Grade 2i` / `Grade 2ii` /
  `Grade 1` (plus `Superseded` / `Regressed`). *Never* a percentage.

=== 9.2 JtV's position

*Status update (later the same day): JtV now holds Grade 3 for four Agda modules.*
The section below is the position *as audited*; it is kept because it explains
why the gap existed, and because every word of it still applies to the theorems
that were **not** ported. `theory/agda/` now carries `Jtv.Core`, `Jtv.Reversal`,
`Jtv.Echo` and `Jtv.Conditional` under the canonical invocation, receipted in
`verification/receipts/2026-11-01-agda.adoc`, with the per-theorem Lean↔Agda
correspondence (and its one strengthening discrepancy) in
`theory/agda/README.adoc` §4. Grade 2i is pending that reconciliation; the Rocq
leg, a non-DTT leg and any Rust/Creusot leg remain absent.

*As audited, JtV held no grade at all.* Not because its proofs were weak, but
because of an ordering choice: JtV mechanised in Lean first, and the estate's
Theory Path puts Agda first. PROOF-POLICY §3 settles the consequence without ambiguity — a Lean
proof of a theory statement is *target-only evidence*, and "the Agda row stays
`OPEN`". JtV has zero `.agda` files. So:

=== 9.3 What this audit therefore does *not* claim

It does not claim JtV's reversibility is "proved". §3 already scopes that
precisely; the estate vocabulary makes the scoping citable: the Safe single-step
and Neutral residue-step theorems are `proven` *over the model and in the wrong
prover for the leg*, the runtime log semantics is `tested-only` at best, the
Neutral round-trip is `open`, and the Rust contracts are `open`.

=== 9.4 The shortest route to Grade 3 (and why it is one theorem, not a suite)

Per PROOF-POLICY §2.3's evidence-first order, keep the Lean and Idris2 gates
running, then take **one exact theorem** to Agda under the canonical invocation
and pin the Agda + stdlib versions with the commit. `dataExpr_totality`
(structural recursion over the `DataExpr` GADT) and the Echo lattice laws are the
cheapest honest candidates: no library dependency, no cubical feature, and the
Lean statement already exists to be compared against. The moment one such
statement type-checks in Agda *and the Lean statement has been compared with it*,
JtV is at Grade 2i — because the Lean leg already exists. Grade 3 alone (Agda,
untranslated) is a state JtV would have to reach by *not* having Lean, so it is
better understood as a milestone on the way, not a destination.

*On the Rust side*, Aeneas is the estate's route for "Rust implements a proved
theorem" — precisely `gap-001` — and it is **not** adoptable today: its Rocq
backend carries an axiom (`mk_array`) from which `False` is derivable and is
unmaintained, and its Lean backend requires Mathlib, which §2 forbids. The
correspondence row would be `ASSUMED` at best. Recorded so no future session
closes the proof-to-interpreter gap with Aeneas and then reports the
implementation as proved.

== §10 One-paragraph answer

JtV v2 remains an independent research-language programme. Its reversible
runtime is JtV's own: an in-process linear token (`u64`) indexing a
per-operation inverse log, with saved-value residues for Neutral
(self-referential) steps and whole-state marshalling at block boundaries. It
depends on no sibling project — not `epistemic-types` (never named in this tree,
which cites `echo-types` instead and only as a conceptual reference), not
*JanusKey* (different abstraction level; mentioned once, in a portfolio status
table), not *Absolute Zero* (sibling verification programme; "CNO" here names a
local runtime identity property). The proof-to-interpreter gap is real and
specific: the Lean model mechanises the Safe single step and the Neutral residue
step per operation, while the executed semantics is a multi-operation log with
conditionals that the model does not cover, and no refinement proof connects the
two. v2 is design-complete with C1/C2 and the Neutral bridge landed; the typed
`ReversalToken<S>`, static linearity, and `irreversible { }` are not implemented,
and the prose that said otherwise is corrected here. JtV's Harvard Data/Control
split and its independently stated reversibility obligations (ADR-0007 D1–D6,
spec §9, ADR-0009, ADR-0010) are untouched. Vocabulary overlap with `epistemic-types`,
*JanusKey* and *Absolute Zero* is recorded as related work with no mapping, and
no dependency is introduced. On the estate's proof grading, JtV holds **no
mathesis grade**: it mechanised in Lean while the Theory Path puts Agda first, so
its seven `sorry`-free libraries are target-only evidence under
`standards/3-practice/PROOF-POLICY.adoc` §3 — a strong artefact in the wrong
prover for the leg, not a weak one — and its first-party Rust carries no Creusot
contracts. Both are recorded, with the ordered path to Grade 3, in
`verification/PROOF-STATUS.adoc`.
